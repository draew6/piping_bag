# piping_bag

Unified CLI and FastAPI integration for database migrations (pgschema) and typed query generation (sqlc). Manages schema as code, generates typed async Python from SQL queries, and handles asyncpg connection pooling.

## Install

```bash
pip install git+https://github.com/draew6/piping_bag@0.6.9.git
```

Requires `pgschema` and `sqlc` on PATH. Python 3.13+.

## Usage via fastlet

Most services use piping_bag through fastlet. In fastlet-based services:

```python
# CORRECT — in fastlet-based services
from fastlet import setup, get_pool, create_queries_dependency

# WRONG — do NOT import from piping_bag directly in fastlet-based services
from piping_bag import setup  # breaks conventions
```

CLI is accessed via `fastlet db <command>` instead of `pb <command>` in fastlet-based services.

## Env vars

```
DATABASE_URL="postgresql://user:pass@localhost:5432/mydb"
```

Single env var. Everything else is derived from it.

## Rules

- NEVER write raw asyncpg pool management — use `setup(app)` or `init_pool()`/`close_pool()`
- NEVER write SQL queries as Python strings — write them in `db/queries/*.sql` with sqlc annotations, then run `pb generate`
- NEVER edit files in `db/generated/` — they are auto-generated by sqlc, changes will be overwritten
- NEVER edit `db/__init__.py` — it is auto-generated by `pb generate` with the unified Queries facade
- NEVER create your own FastAPI dependency for database connections — use `QueriesDep` from `db/__init__.py`
- NEVER import from `db.generated` directly in routes — import `QueriesDep` from `db`
- NEVER import from piping_bag in fastlet-based services — import from fastlet instead
- ALWAYS define schema in `db/schema.sql` — this is the single source of truth
- ALWAYS run `pb up` (or `fastlet db up`) after changing schema or queries — it applies migrations and regenerates code
- ALWAYS use sqlc annotations in query files (`-- name: QueryName :one/:many/:exec`)

## Architecture

```
db/schema.sql  →  pgschema plan/apply  →  SQLC  →  Python Client
       ↓                   ↓                ↓           ↓
   (desired state)   (live DB updated)  (queries/)  (models.py, queries.py)
```

## Project structure

```
db/
  __init__.py         # AUTO-GENERATED — unified Queries facade + QueriesDep
  schema.sql          # SOURCE OF TRUTH — define tables here
  queries/            # Write SQL queries here with sqlc annotations
    users.sql
    postings.sql
  generated/          # AUTO-GENERATED — never edit
    __init__.py
    models.py         # dataclasses from schema
    queries.py        # typed async query functions
sqlc.yaml             # sqlc config (created by pb init)
.env                  # DATABASE_URL
```

## Workflow

### Starting a new service with a database

```bash
pb init              # scaffolds db/, sqlc.yaml, .env
# edit .env with DATABASE_URL
# edit db/schema.sql with your schema
# write queries in db/queries/*.sql
pb up                # applies schema + generates Python client
```

### Day-to-day: changing schema or queries

```bash
# 1. Edit db/schema.sql and/or db/queries/*.sql
# 2. Run:
pb up                # applies migration + regenerates code
```

That's it. `pb up` = `pb apply` + `pb generate`.

### Just checking what would change

```bash
pb diff              # shows planned schema changes (human-readable)
pb plan              # detailed migration plan
```

## Writing queries

Use sqlc annotations in `db/queries/*.sql`:

```sql
-- name: GetUser :one
SELECT * FROM users WHERE id = $1;

-- name: ListUsers :many
SELECT * FROM users ORDER BY created_at DESC LIMIT $1;

-- name: CreateUser :one
INSERT INTO users (email, name) VALUES ($1, $2) RETURNING *;

-- name: UpdateUser :exec
UPDATE users SET name = $2 WHERE id = $1;

-- name: DeleteUser :execrows
DELETE FROM users WHERE id = $1;
```

### Query commands

| Command | Returns | Use case |
|---|---|---|
| `:one` | Single row or None | Fetch by ID |
| `:many` | List of rows | List queries |
| `:exec` | None | Updates without return |
| `:execrows` | Row count (int) | Delete/update with count |
| `:execresult` | Driver result object | Full result access |
| `:execlastid` | Last inserted ID | Insert without RETURNING |
| `:copyfrom` | None | Bulk insert (asyncpg) |

After `pb generate`, these become typed async methods on the Queries class.

## FastAPI integration

```python
import piping_bag
from fastapi import FastAPI
from db import QueriesDep

app = FastAPI()
piping_bag.setup(app)  # manages asyncpg pool lifecycle automatically

@app.get("/users/{user_id}")
async def get_user(user_id: int, queries: QueriesDep):
    return await queries.get_user(id=user_id)

@app.get("/users")
async def list_users(queries: QueriesDep):
    return await queries.list_users(limit=100)

@app.post("/users")
async def create_user(email: str, name: str, queries: QueriesDep):
    return await queries.create_user(email=email, name=name)
```

`setup(app)` composes with any existing lifespan — it wraps it, doesn't replace it.

`QueriesDep` acquires a connection per request from the pool, auto-releases after response.

## Manual pool management (rare, for scripts/workers)

```python
from piping_bag import init_pool, close_pool, get_pool

await init_pool("postgresql://user:pass@localhost:5432/mydb")
pool = get_pool()
async with pool.acquire() as conn:
    result = await conn.fetch("SELECT 1")
await close_pool()
```

## How code generation works

`pb generate` does two things:

1. Runs `sqlc generate` which reads `db/queries/*.sql` + `db/schema.sql` → produces `db/generated/` with typed dataclass models and async query methods
2. Scans `db/generated/` for query classes → produces `db/__init__.py` with a unified `Queries` facade that merges all query classes and exposes `QueriesDep`

If you have multiple query files (`users.sql`, `postings.sql`), each gets its own class in `db/generated/`, but `db/__init__.py` unifies them so you access everything through one `QueriesDep`.

## CLI reference

| Command | What it does |
|---|---|
| `pb init` | Scaffold db/, sqlc.yaml, .env |
| `pb plan` | Show planned migration (diff schema.sql vs live DB) |
| `pb apply` | Apply migration |
| `pb sync` | Plan + apply in one step |
| `pb generate` | Run sqlc + generate db/__init__.py |
| `pb up` | Apply + generate (the main command) |
| `pb dump` | Dump live DB schema to db/schema.sql |
| `pb diff` | Show planned changes (human-readable) |
| `pb studio` | Open Prisma Studio |
| `pb sql` | Open Harlequin SQL IDE |

## Tech stack

**Python dependencies** (in pyproject.toml):
- **asyncpg** — PostgreSQL driver
- **pydantic-settings** — Environment configuration
- **typer** — CLI framework

**External CLI tools** (must be installed separately):
- **pgschema** — Declarative schema definition + migrations
- **sqlc** with **sqlc-gen-better-python** — Generates Python client from SQL queries
- **prisma** — Studio only (introspect DB → GUI browsing)
- **harlequin** — Terminal-based SQL IDE (`pip install harlequin[postgres]`)

## Limitations

- Enums not supported yet in sqlc-gen-better-python
- `:batch*` commands not supported
- Prepared queries not yet implemented
- psycopg2 and mysql drivers not implemented

## Architecture internals

- `config.py` — `PipingBagConfig` with `DATABASE_URL`, `parse_database_url()` for pgschema env vars
- `fastapi.py` — asyncpg pool management (`setup`, `init_pool`, `close_pool`, `get_pool`, `create_queries_dependency`)
- `cli.py` — typer CLI wrapping pgschema + sqlc + db/__init__.py generation
- `runner.py` — subprocess runner with binary availability checks
- `templates/` — scaffolding templates for `pb init`

## Testing

Uses testcontainers for real PostgreSQL in tests:

```python
from testcontainers.postgres import PostgresContainer
import asyncpg

with PostgresContainer("postgres:17") as pg:
    url = f"postgresql://test:test@{pg.get_container_host_ip()}:{pg.get_exposed_port(5432)}/test"
    pool = await asyncpg.create_pool(url)
```

Requires Docker running. Run with `pytest tests/ -v`.
